Substantially redesign the existing frontend for its actual deployment environment.

First inspect the existing frontend implementation and tests. Preserve the backend/API architecture and existing calendar behavior unless a frontend change requires a small adjustment. This task is primarily a visual/interaction redesign, not an architectural rewrite.

CONTEXT

This application will run continuously in a full-screen/kiosk browser on a dedicated wall-mounted 27-inch 4K touchscreen (3840x2160, 16:9).

The current frontend is an initial prototype, but it feels like a conventional desktop website enlarged onto a big display. It uses too little of the available screen, contains excessive whitespace, has calendar text and controls that are too small for distance viewing, and currently permits document scrolling.

Redesign it as a purpose-built household information appliance.

PRIMARY DESIGN GOALS

1. ONE-SCREEN KIOSK COMPOSITION

At the target 16:9 aspect ratio, the complete primary dashboard must fit within one viewport with no document-level vertical or horizontal scrolling.

Treat 100dvw x 100dvh as a fixed physical canvas.

The browser must not need to scroll to see the current month/week, today's agenda, navigation, or important household status.

Individual overlays, dialogs, or unusually long detail panels may scroll internally if necessary.

Do not solve this by simply shrinking content.

The design should deliberately allocate the entire screen.

2. DESIGN FOR TWO VIEWING DISTANCES

Ambient viewing:
- roughly across a kitchen/room
- immediately readable date/time
- immediately understandable calendar
- today's important events and times easily readable
- useful status visible without interaction

Walk-up/touch viewing:
- richer event information
- obvious controls
- large touch targets
- easy calendar navigation
- easy event selection
- eventual voice interaction

Prioritize functional information hierarchy over decorative whitespace.

3. MAKE THE CALENDAR THE VISUAL CENTER OF GRAVITY

The calendar is the primary purpose of the display.

Replace the current sparse "numbers floating in whitespace" treatment with a strong calendar grid.

For the month view:
- clear day-cell boundaries or other strong spatial grouping
- large, readable date numbers
- visually prominent current day
- enough room inside each visible day for several color-coded event summaries
- event time + concise event title when appropriate
- clear all-day event treatment
- graceful handling of overflow
- household/person/calendar colors must remain recognizable at a distance
- previous/next month navigation must have large touch targets

A user looking at the screen from several feet away should be able to tell that this is September 2026, identify today, and understand the important schedule without approaching the display.

4. REWORK THE OVERALL LAYOUT

Do not preserve the current layout merely because it already exists.

Develop a stronger information architecture optimized specifically for the display.

A reasonable starting composition is:

+------------------------------------------------------+
| compact global header: date/time/status/actions      |
+--------------------------------------+---------------+
|                                      | TODAY /       |
|                                      | NEXT UP       |
|          PRIMARY CALENDAR            |               |
|                                      | agenda        |
|                                      |               |
|                                      +---------------+
|                                      | HOME STATUS   |
+--------------------------------------+---------------+
| optional compact contextual/navigation/voice area    |
+------------------------------------------------------+

This is guidance, not a mandatory pixel layout. Improve on it if the existing application suggests something better.

The primary calendar should receive approximately 70-80% of the useful horizontal area.

Avoid a large decorative greeting such as "Good morning, everyone" consuming valuable prime screen area. If a greeting is retained, make it subordinate to useful information.

5. TYPOGRAPHY AND DISTANCE READABILITY

Explicitly establish a typography scale for a large physical display.

There should be a strong hierarchy for:
- current time
- current date / month
- calendar dates
- event times
- event names
- agenda items
- secondary/status text
- labels

The current tiny uppercase section labels and pale low-contrast text are inappropriate for important information.

Use muted text only for genuinely secondary information.

Maintain strong contrast and readability in normal indoor lighting.

6. TOUCH UX

Assume interaction by fingertip rather than mouse.

Make interactive targets comfortably large, including:
- previous/next calendar navigation
- event cards
- Add
- calendar/person filters
- any mode/navigation controls

Do not require hover for important information or functionality.

Provide clear pressed/selected/focus states.

Avoid tiny chevrons or text-only click targets.

7. PREPARE FOR FUTURE VOICE INTERACTION

Do not implement speech or AI in this task.

However, reserve a visually coherent way for voice interaction to appear later, for example:
- an unobtrusive microphone affordance while idle
- a listening/thinking state
- transcript/result overlay
- confirmation UI for proposed actions

Voice UI should overlay or temporarily transform part of the dashboard rather than permanently consuming a large empty region.

8. RESPONSIVENESS

Optimize first for the actual 3840x2160 16:9 kiosk.

Also make the layout behave sensibly when developed in a normal desktop browser at smaller 16:9 resolutions such as 1920x1080.

Use responsive units, CSS grid/flex, clamp(), design tokens, or similar techniques where useful.

Do not create a design that happens to fit 3840x2160 only because of hard-coded pixel coordinates.

The important invariant is:
- no page-level scrolling at 16:9 desktop/kiosk sizes
- deliberate bounded layout
- information hierarchy remains similar as viewport size changes

9. VISUAL CHARACTER

Aim for:
- calm
- polished
- modern
- high-information but uncluttered
- warm enough for a home
- appliance-like rather than SaaS-dashboard-like

Avoid:
- excessive whitespace
- giant marketing-style headings
- tiny typography
- glassmorphism for its own sake
- excessive rounded cards
- gradients/decorative effects that reduce legibility
- a generic admin dashboard appearance
- mimicking Outlook or Google Calendar too closely

Use color principally to communicate calendar/person identity, status, selection, and hierarchy.

Do not rewrite working backend code unnecessarily.

DEFINITION OF DONE

The result should look plausible if the browser chrome were removed and the display were mounted permanently on a kitchen wall.

At 3840x2160:
- the application occupies exactly one viewport
- there is no document scrollbar
- the whole useful current calendar view is visible
- the calendar dominates the display
- event information is substantially more readable than the current prototype
- today's agenda is prominent
- touch targets are obviously usable
- unused whitespace feels intentional rather than accidental
- important information can plausibly be read from several feet away

Before finishing, compare the rendered implementation explicitly against these criteria and fix obvious failures rather than merely reporting them.

- a concise summary of the frontend redesign
